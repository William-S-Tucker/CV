Airflow Field Guide

Apache Airflow is the best-known orchestration tool, the thing that runs each pipeline step in the right order and tells you when one fails. The posting says Minga's stack "runs on good intentions today." This guide explains what orchestration would change.

The one-minute version

  • You write workflows in Python as DAGs (directed acyclic graphs): a set of tasks plus the order they run in.
  • Airflow's scheduler starts each run on time, runs each task once the tasks before it succeed, retries failures, and records every run's state.
  • It's a conductor, not an engine. Tasks tell other systems (Stitch, Snowflake, dbt) to do the heavy work, then wait for the result.
  • Version 3.0 came out in April 2025 with a new UI, DAG versioning, and "assets" for data-aware scheduling. Most tutorials online still show version 2.
  • Alternatives in the same category: Dagster and Prefect. The posting only asks for working knowledge of at least one orchestration tool, so any of them counts.

Where it sits at Minga

The posting: "Own ingestion end to end: harden or replace our current Stitch pipelines and bring proper orchestration to a stack that runs on good intentions today."

The problem it solves

Without an orchestrator, each tool runs on its own clock. Stitch syncs on its schedule, dbt runs at a fixed time on a cron job, and everyone hopes the load finished first. Usually it does. When it doesn't, dashboards show half-loaded data and nobody gets told.

An orchestrator gives you four things the stack lacks today: dependencies (run B after A succeeds), retries (try a flaky API call again), alerting (tell someone when it fails), and history (what ran, when, how long, and what broke).

Core ideas

TermMeaning
DAGOne workflow: its tasks, their order, and its schedule. A Python file in the dags/ folder. "Acyclic" means no loops.
TaskOne step in a DAG, e.g. "trigger Stitch" or "run dbt build".
OperatorA ready-made task type. BashOperator runs a shell command, SQLExecuteQueryOperator runs SQL, and provider packages add operators for Snowflake, dbt Cloud, Slack, and more.
SensorA task that waits for something: a file to appear, an API to report "done".
TaskFlowThe modern style: plain Python functions decorated with @task, inside a function decorated with @dag.
DAG runOne execution of a DAG. Each has a logical date and a data interval, the slice of time it's responsible for.
RetriesHow many times a failed task is retried, and how long to wait between tries.
BackfillRunning a DAG for past intervals, e.g. to rebuild last month after fixing a bug.
ConnectionsStored credentials (Snowflake, Stitch API token) kept out of the code. Can come from a secrets manager.
XComSmall values passed between tasks, like a job ID. Never use it for datasets.
Asset(Airflow 3) A named piece of data. A DAG can be scheduled to run when an asset is updated instead of on a clock.

A DAG for Minga, sketched

This is a teaching sketch of a nightly pipeline: trigger the Stitch sync, wait for it, check freshness, build dbt, and alert on failure. It's in Airflow 3 style. Read it for the shape, not as production code.

dags/nightly_warehouse.py

from pendulum import datetime
from airflow.sdk import dag, task
from airflow.providers.standard.operators.bash import BashOperator


def alert_on_failure(context):

@dag(
    schedule="0 5 * * *",                         # 5:00 every day
    start_date=datetime(2026, 10, 1, tz="America/Vancouver"),
    catchup=False,                                 # don't auto-run missed past days
    default_args={
        "retries": 2,
        "retry_delay": timedelta(minutes=5),
        "on_failure_callback": alert_on_failure,
    },
)

    @task
    def trigger_stitch_sync() -> str:
        # call Stitch's API to start the sync; the token comes from an
        # Airflow Connection, never from this file
        ...
        return job_id

    def wait_for_stitch(job_id: str):
        # ask Stitch every 5 minutes whether the sync finished;
        # give up and fail after 3 hours
        ...

    freshness = BashOperator(
        task_id="dbt_source_freshness",
        bash_command="cd /opt/dbt && dbt source freshness --target prod",
    )

    build = BashOperator(
        task_id="dbt_build",
        bash_command="cd /opt/dbt && dbt build --target prod",
    )

    wait_for_stitch(trigger_stitch_sync()) >> freshness >> build


nightly_warehouse()
  • >> sets the order. Passing trigger_stitch_sync() into wait_for_stitch sets it too, and hands over the job ID.
  • mode="reschedule" frees the worker slot between checks instead of holding it for 3 hours.
  • Running dbt as one dbt build task is the simplest option. The open-source Cosmos package (from Astronomer) instead turns each dbt model into its own Airflow task, so you can see and retry a single model.

How Airflow runs

  • Executor: how tasks reach workers. LocalExecutor runs them on the same machine. CeleryExecutor uses a queue (Redis) and a pool of workers, like n8n's queue mode. KubernetesExecutor starts a pod per task.
  • Keep DAG files light. The DAG processor re-parses them constantly, so no database calls or API calls at the top level of the file.
  • Managed Airflow means someone else runs all of this: Astronomer (Astro), Amazon MWAA, or Google Cloud Composer. For a one-person data team, that's usually the right call.

What makes a pipeline reliable

PracticeWhy
Idempotent tasksRunning a task twice gives the same result as running it once, so retries and backfills are safe. You built this into CDWTool: duplicate protection per reporting period.
Retries with a delayMost API failures are temporary. Two or three retries a few minutes apart clear most of them.
TimeoutsA hung task should fail loudly, not run all night.
Alerts that are testedAn alert path you've never seen fire might not work. Same lesson as your n8n deliberate-failure test.
Process by data intervalEach run handles "its" slice of time, so reruns and backfills don't double-count.
Heavy work outside AirflowWorkers call Snowflake and Stitch. They don't load millions of rows into their own memory.
Secrets in ConnectionsCredentials in Airflow Connections or a secrets manager, never in the DAG file or git.

Keep it accurate

The honest line is: "I haven't run Airflow or another dedicated orchestrator. I've built workflow automation with n8n in queue mode, with retries, a tested error handler, and workflows deployed from git, so the concepts are familiar. The tool is new to me."

Interview-ready answers

If asked: "What orchestration have you used?"
"No dedicated orchestrator in production. I built and run an n8n stack in queue mode: per-source retries, a global error handler I proved with a deliberate failure, and workflows generated by a Python script and deployed from git. So I know the problems an orchestrator solves. Airflow and Dagster would be new tools for me, not new ideas."
"How would you bring orchestration to our stack?"
"First, make the steps depend on each other: load, check freshness, transform, test, and alert a human when something fails. Then pick the tool. As the only data engineer I'd want it managed rather than another server to babysit, and I'd look at what the platform team already runs. Between managed Airflow and Dagster+, I'd lean on which fits dbt and the team best, and I'd want to try both on a real pipeline first."
Good questions to ask them
  • How do you find out today when a Stitch sync fails?
  • What does the Platform & SRE team already run (AWS, Kubernetes, anything managed)?
  • Is there an orchestrator in use elsewhere in engineering I should align with?

Flashcards

What is a DAG?

A directed acyclic graph: a workflow's tasks and the order they run in, with no loops. In Airflow, a Python file.

Operator vs sensor?

An operator does something (run SQL, run a command). A sensor waits for something (a file, an API status) before the next task starts.

What does the scheduler do?

Decides which DAG runs and tasks are due, based on schedules and whether upstream tasks succeeded, and queues them for workers.

Why must tasks be idempotent?

So retries and backfills are safe: running a task twice for the same interval gives the same result instead of duplicates.

What is catchup?

Whether Airflow automatically runs every missed interval since start_date. Off by default in Airflow 3. Backfills do it on purpose.

Where do credentials live?

In Airflow Connections, optionally backed by a secrets manager. Never in DAG code.

What's the main difference with Dagster?

Airflow schedules tasks. Dagster models data assets (tables, models) and their lineage, which fits dbt naturally.

What changed in Airflow 3?

Released April 2025: new React UI, DAG versioning, assets (renamed from datasets), a Task Execution API between workers and the core, and catchup off by default.

Try it yourself

You already run Docker Compose, so a local Airflow is an evening's work.

  • Install the Astronomer CLI and run astro dev init then astro dev start. It starts a local Airflow in Docker with the UI at localhost:8080. (Or pip install apache-airflow and airflow standalone.)
  • Write a three-task TaskFlow DAG and watch it in the grid view.
  • Make one task fail on purpose. Watch the retries, then the failure callback fire.
  • Add a Snowflake connection to your trial account and run a dbt build from a task.
  • Optional: install astronomer-cosmos and render your jaffle shop dbt project as an Airflow task group.
