dbt Field Guide

dbt is the "modelling layer" the posting wants you to introduce. It's SQL in version control, with tests and code review, and it runs inside Snowflake. That's very close to how you already work, which makes it your best bridge in the interview.

The one-minute version

  • dbt (data build tool) handles the T in ELT. Stitch extracts and loads raw data. dbt transforms it into clean tables people can trust.
  • You write each table as a SELECT statement in a .sql file. dbt wraps it in CREATE TABLE/VIEW AS and runs it in Snowflake.
  • Models refer to each other with ref(). dbt uses that to work out the run order, so you never write a dependency list by hand.
  • Tests (unique, not null, valid values, relationships, freshness) run after each build. The whole project lives in git and goes through pull requests like any other code.
  • dbt doesn't move data and doesn't need its own server for the data. All the compute happens in Snowflake.

Where it sits at Minga

The posting: "Introduce and own a modelling layer (dbt or equivalent) with versioning, tests and review that our RevOps analysts can build against without slowing down." Today there isn't one. Raw Stitch tables go more or less straight to Metabase, with the logic buried in dashboard queries.

What a model is

A model is one .sql file containing one SELECT. The file name becomes the table or view name. Here's a staging model over an illustrative raw table:

models/staging/app/stg_app__hall_passes.sql

with source as (
    select * from {{ source('app', 'hall_passes') }}
),

renamed as (
    select
        id                          as pass_id,
        school_id,
        student_id,
        lower(status)               as status,
        started_at::timestamp_ntz   as started_at,
        ended_at::timestamp_ntz     as ended_at,
        _sdc_batched_at             as loaded_at
    from source
)

select * from renamed

The {{ }} parts are Jinja, a templating language. When you run dbt, it compiles the file into plain SQL for Snowflake:

create or replace view analytics.staging.stg_app__hall_passes as (
    with source as (
        select * from raw.app.hall_passes
    ),
    ...
);

That's the core idea. You write SELECT, and dbt handles the DDL, the schema names, and the environment (your dev schema or production).

ref() and the dependency graph

Instead of hard-coding table names, a model says {{ ref('stg_app__schools') }}. That does two things: it points at the right schema for the current environment, and it tells dbt "this model depends on that one". dbt collects every ref() and source() into a graph and runs models in order.

Staging, intermediate, marts

The convention dbt Labs recommends, and the one most teams follow:

LayerWhat goes in itUsually built as
Staging stg_One model per raw table. Rename, cast types, fix obvious mess. No joins, no business logic. The only layer that reads source().Views
Intermediate int_Joins and business logic that's reused, kept out of sight of analysts.Views or ephemeral
Marts fct_ / dim_Facts (events, things that happen: passes, behaviour entries, invoices) and dimensions (things: schools, districts, accounts). This is what Metabase and analysts read.Tables or incremental

Think of it like your Oracle reporting work: raw extracts, then cleaned views, then the reporting tables people query. The difference is that every step is a file in git with tests attached.

Materializations

A model's materialization decides what dbt builds in Snowflake. You set it in the model or for a whole folder in dbt_project.yml.

TypeWhat it createsUse when
viewA view. Nothing stored. Computed when queried.Staging. Cheap to build, light to query.
tableA full table, rebuilt from scratch every runMarts that are small or medium sized
incrementalA table where each run only processes new or changed rowsBig event tables. This is a major cost lever.
ephemeralNothing. Inlined as a CTE into models that use it.Small helper logic

models/marts/fct_hall_passes.sql (incremental)

{{ config(materialized='incremental', unique_key='pass_id') }}

select * from {{ ref('stg_app__hall_passes') }}

{% if is_incremental() %}
  -- only on later runs: rows newer than what's already in this table
  where loaded_at > (select max(loaded_at) from {{ this }})
{% endif %}

On the first run, dbt builds the whole table. After that it merges only new rows, using unique_key to update rows that changed. dbt build --full-refresh rebuilds it from scratch when the logic changes.

Tests and freshness

Tests are declared in YAML next to the models. Each one compiles to a query that returns the rows that break the rule. Zero rows means it passes.

models/staging/app/_app__models.yml

models:
  - name: stg_app__hall_passes
    description: One row per hall pass issued in the Minga app.
    columns:
      - name: pass_id
        data_tests: [unique, not_null]
      - name: status
        data_tests:
          - accepted_values:
              values: ['active', 'ended', 'expired']
      - name: school_id
        data_tests:
          - relationships:
              to: ref('stg_app__schools')
              field: school_id
  • Generic tests: the four built-ins above (unique, not_null, accepted_values, relationships), plus many more from the dbt_utils and dbt_expectations packages.
  • Singular tests: any SQL file in tests/ that returns bad rows, e.g. "no pass ends before it starts".
  • Unit tests (dbt 1.8 and later): feed a model fixed input rows and check the exact output. This tests the logic itself, like your golden-file tests in AscendAI.
  • Model contracts: lock a mart's column names and types, so a change that would break a dashboard fails the build instead.

Source freshness: catching a silent Stitch failure

sources:
  - name: app
    database: raw
    loaded_at_field: _sdc_batched_at
    freshness:
      warn_after: {count: 6, period: hour}
      error_after: {count: 24, period: hour}
    tables:
      - name: hall_passes

dbt source freshness checks when each source last received data. If Stitch quietly stops syncing, this fails before anyone notices stale numbers in a dashboard. It's a direct answer to "a stack that runs on good intentions today."

The review workflow

The posting asks you to "set the standard for how data work gets reviewed when a model can write the first draft." In dbt, that standard is the pull request plus CI:

  • Environments: each developer builds into their own schema (dbt_william) using a dev target. Production builds into analytics. Same code, different target in profiles.yml.
  • Slim CI: dbt build --select state:modified+ --defer --state prod-artifacts/ builds only what changed plus downstream, and reads unchanged upstream models from production. Fast and cheap.
  • What a reviewer checks: does the SQL make sense, are keys tested, did row counts change unexpectedly (a "data diff" against production), is new PII tagged, are docs written.
Your angle on AI review

When AI writes the first draft, the risk isn't syntax. It's SQL that runs fine and quietly produces wrong numbers: a join that duplicates rows, a filter that drops a school. The answer is tests that catch exactly that (unique keys, relationships, row-count checks, unit tests on tricky logic), plus a human reading the diff. That's the same discipline as your golden-file tests and your guarded Oracle MCP server: let the model draft, and don't let it ship unchecked.

Snapshots, docs, and grants

Snapshots: keeping history Stitch doesn't

Stitch replicates the current state of a row. If a school's plan changes from Basic to Premium, the old value is gone. A dbt snapshot records each change as a new row with dbt_valid_from and dbt_valid_to (a "slowly changing dimension, type 2"). Finance and RevOps usually need this for questions like "what was this account's plan at renewal?"

Docs and lineage

dbt docs generate builds a browsable site from your YAML descriptions, with the lineage graph above. Exposures let you declare which Metabase dashboards depend on which models, so you can see what breaks before you change something. This is how analysts learn to self-serve: they look up what a column means instead of asking you.

Access control as code

# dbt_project.yml
models:
  minga:
    marts:
      +materialized: table
      +grants:
        select: ['REPORTER', 'ANALYST']

dbt re-applies grants every time it builds, so permissions can't drift away from what's in git. Snowflake masking policies can be attached to tagged columns from dbt too, which ties this guide to the PII section of the Snowflake guide.

Interview-ready answers

If asked: "Have you used dbt?"
"Not in production. But dbt is SQL in version control, reviewed, tested, and deployed through CI, and that's how I already work. Most of the learning is its conventions: ref and source, the staging-to-marts layering, the testing YAML. The judgement parts, what to test and how to keep student data out of the wrong places, I bring with me."
"How would you introduce dbt here?"
"Start small and visible. Find the five Metabase dashboards people rely on most, trace them back to the raw Stitch tables, and build staging models for just those sources, with key tests and source freshness. Then build marts behind those dashboards and repoint them. Analysts see better numbers in weeks, and the pattern is set for everything after."
"How would you let RevOps analysts build without slowing down?"
"Clear layers so they know where to build, a short style guide, docs they can browse, and a pull-request template with the checks I'd look for. Reviews should be fast, and CI should catch the mechanical problems, so my review is about the logic. Same thing I did at TRU teaching staff to run their own reporting."

Flashcards

What does dbt actually do?

Compiles SELECT-statement models (SQL + Jinja) into DDL, runs them in the warehouse in dependency order, and tests the results. It doesn't move data.

ref() vs source()?

source() points at raw tables loaded by something else (Stitch). ref() points at another dbt model. Both add edges to the dependency graph.

Name the four built-in generic tests.

unique, not_null, accepted_values, relationships.

When would you make a model incremental?

When it's large and append-heavy (events). Each run processes only new or changed rows, saving time and Snowflake credits.

What is a snapshot for?

Keeping history of rows that get overwritten in the source (type 2 slowly changing dimension), using dbt_valid_from and dbt_valid_to.

What does state:modified+ do in CI?

Selects only models changed in this branch plus their downstream, comparing against the production manifest. Used with --defer for fast "slim CI".

What are staging models allowed to do?

Rename, cast, light cleaning. One per source table. No joins or business logic. They're the only models that read source().

How does dbt help self-serve?

Generated docs with column descriptions and lineage, exposures that link dashboards to models, and a reviewed path for analysts to contribute their own models.

Try it yourself

dbt Core is free, and dbt Labs publishes a sample project called jaffle shop (a made-up sandwich shop) built for learning. Pair it with the Snowflake trial:

  • python -m pip install dbt-core dbt-snowflake, then dbt init and point it at your trial account.
  • Load the jaffle shop CSVs with dbt seed, or declare a Snowflake sample table as a source.
  • Write two staging models and one mart that joins them, using ref().
  • Add unique and not_null tests, break one on purpose, and watch dbt build fail.
  • Convert the mart to incremental and run it twice.
  • Run dbt docs generate and dbt docs serve and look at the lineage graph.
  • Put it in a GitHub repo with a GitHub Actions job that runs dbt build on pull requests. That's a small, real demo of "review standards for data work."
