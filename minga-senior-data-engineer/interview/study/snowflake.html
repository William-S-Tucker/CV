Snowflake Field Guide

Snowflake is the cloud data warehouse Minga already runs on. This guide explains it in terms of the Oracle work you already know, then covers the two things the posting cares about most: cost and student data.

The one-minute version

  • A SQL database delivered as a service. No servers, tablespaces, indexes, or patching. You write SQL and it runs.
  • Storage and compute are separate. One copy of the data sits in cloud storage. Compute comes from virtual warehouses, which are clusters you switch on and off.
  • You pay for storage (cheap) and for every second a warehouse is running (where the money goes). Costs come from warehouses left running.
  • Access is role-based, like Oracle grants. Enterprise edition adds column masking and row-level policies, which is how you'd protect student PII.

Where it sits at Minga

The posting names the stack: Stitch pulls data out of the product and business tools, loads it into Snowflake, and analysts read it through Metabase. Snowflake is the centre: everything lands there, gets transformed there, and gets queried there.

How it's built

Snowflake has three layers. Once you see them, most of its behaviour (and its bill) makes sense.

  • Cloud services is the brain: authentication, the optimizer, metadata, and security policies. Mostly free (it's billed only if it goes over 10% of your daily warehouse usage).
  • Virtual warehouses are the muscle. They start in seconds, suspend themselves when idle, and come in T-shirt sizes.
  • Storage is the memory. Tables are split into compressed, column-oriented files called micro-partitions. You never manage files.

Snowflake runs on AWS, Azure, or Google Cloud. You pick a cloud and region when the account is created, but you never touch that cloud directly.

Oracle to Snowflake, side by side

Most of your SQL carries over. Snowflake supports NVL, DECODE, MERGE, CONNECT BY, analytic functions, and CTEs, and unquoted identifiers default to uppercase like Oracle. The differences are in everything around the SQL.

Warehouses and cost

The posting says: "Keep Snowflake and pipeline costs proportional to usage, and know exactly why when they aren't." That's all about warehouses.

SizeCredits per hourRule of thumb
X-Small1Most loading and BI at Minga's scale
Small2Typical dbt runs
Medium4Heavy transforms, big backfills
Large8Rarely needed at this size of company
X-Large and up16, 32 …Each size doubles the cost and roughly the speed

A credit costs roughly $2 to $4 USD depending on edition, cloud region, and contract. Billing is per second, with a 60-second minimum every time a warehouse resumes. Two settings control most of the bill:

  • AUTO_SUSPEND = 60 turns the warehouse off after 60 idle seconds.
  • AUTO_RESUME = TRUE turns it back on when a query arrives.

Where surprise bills come from

  • Frequent loads. If Stitch syncs every 30 minutes, it wakes the loading warehouse 48 times a day, and each wake-up bills at least 60 seconds. Sync frequency is a cost setting.
  • Dashboards on auto-refresh. A Metabase dashboard left open on a wall screen keeps the BI warehouse awake all day.
  • Oversized warehouses. Someone bumped a warehouse to Large for one backfill and never set it back.
  • Full rebuilds. dbt rebuilding big tables from scratch every hour when an incremental model would do.

How you find out why

-- Credits per warehouse per day, last 30 days
select warehouse_name,
       date_trunc('day', start_time) as day,
       sum(credits_used)              as credits
from snowflake.account_usage.warehouse_metering_history
where start_time >= dateadd('day', -30, current_timestamp())
group by 1, 2
order by 2, 3 desc;
  • One warehouse per workload (loading, transforming, BI), so the bill already tells you who spent it.
  • Query tags (ALTER SESSION SET QUERY_TAG = 'dbt:nightly') to attribute spend inside a warehouse. dbt can set these for you.
  • Resource monitors: a monthly credit quota per warehouse that notifies you at, say, 80% and can suspend the warehouse at 100%.
  • The result cache: if someone reruns an identical query within 24 hours and the data hasn't changed, Snowflake returns the cached result without starting a warehouse. That's free.

No indexes: how queries stay fast

Snowflake stores the minimum and maximum value of every column for every micro-partition. When a query filters, it skips any partition whose range can't contain a match. This is called pruning, and it does the job indexes do in Oracle.

Pruning works well when you filter on a column that follows load order, like dates. If you filter on something scattered (a school ID that appears in every partition), nothing gets skipped. For very large tables you can add a clustering key so Snowflake keeps rows with similar values together. That re-sorting runs in the background and costs credits, so only use it when the Query Profile shows poor pruning on a big table.

Loading data, and JSON

Snowflake's own loading tools are stages (an internal area, or an S3/Azure/GCS bucket) plus COPY INTO, and Snowpipe for loading files as they arrive. At Minga, Stitch handles this. A few Stitch details worth knowing before you're asked to "harden or replace" it:

  • Stitch usually writes each source into its own schema in a raw database and adds metadata columns such as _sdc_batched_at and _sdc_extracted_at. Those are your freshness signal.
  • It replicates tables by key-based incremental (an updated_at column), log-based (database change logs), or full table. Hard deletes in the source can be missed with key-based incremental, so a student record removed in the product can survive in Snowflake. That matters for retention rules.
  • When a source column changes type, Stitch can split it into new columns with a type suffix. Staging models in dbt are where you clean that up.
  • Common replacements are Fivetran and Airbyte. Writing custom loaders in Python is another option.

Product event data usually arrives as JSON. Snowflake keeps it in a VARIANT column and you query it with a path syntax:

select
  payload:student_id::number      as student_id,
  payload:pass.type::string       as pass_type,
  f.value:name::string            as tag_name
from raw.app.events,
     lateral flatten(input => payload:tags) f   -- one row per tag in the JSON array
where payload:event_type::string = 'pass_started';

This connects to the posting's "analytics event model for the new platform": you'll help decide what those JSON events look like before they're ever written.

Access control and student PII

This is the part of the job closest to what you already do. The posting says it twice: "We hold student-level data and we treat it that way."

Roles

Snowflake ships with system roles. ACCOUNTADMIN is the top and should belong to very few people, with MFA on. SECURITYADMIN manages grants, SYSADMIN owns databases and warehouses, USERADMIN creates users, and PUBLIC is granted to everyone. Anything granted to PUBLIC is a red flag. Masking and row policies

A masking policy is a function attached to a column. Every query runs through it, so it works the same in Metabase, a worksheet, or a dbt model.

create masking policy pii_string as (val string) returns string ->
  case when is_role_in_session('PII_READER') then val
       else '****'
  end;

alter table analytics.marts.dim_students
  modify column student_name set masking policy pii_string;
  • Row access policies filter rows by role. For example, a CX role only sees schools in the region it supports. This is like Oracle VPD.
  • Tag-based masking: tag columns as pii = 'name' or pii = 'email' and attach the policy to the tag. New PII columns are protected as soon as they're tagged.
  • ACCESS_HISTORY records which columns each query read, so you can answer "who looked at student data last month?"
  • Masking, row access policies, and access history need Enterprise edition or higher. Ask which edition Minga is on.

Secrets and service accounts

Service users should sign in with key-pair authentication (or OAuth), not passwords. Snowflake has been phasing out password-only sign-in. This is the same instinct as moving CDWTool onto a dedicated Ministry service account and getting secrets out of the repo, and that's a real story you can tell.

Retention

Deleting student data isn't instant in Snowflake. Deleted rows stay recoverable through Time Travel for the table's retention period, then sit in Fail-safe for 7 more days, where only Snowflake support can recover them. A retention standard has to account for both. It also has to cover copies in Metabase caches and in any clones.

Time Travel and zero-copy clones

-- What did this table look like an hour ago?
select * from marts.fct_hall_passes_daily at(offset => -3600);

-- Someone dropped it by mistake
undrop table marts.fct_hall_passes_daily;

-- A full copy of production for testing, created in seconds, no extra storage until it changes
create database analytics_ci clone analytics;
  • Time Travel retention defaults to 1 day. Enterprise edition allows up to 90. Longer retention means more storage cost and longer-lived copies of PII.
  • Zero-copy clones share the original's micro-partitions and only store what changes afterwards. They make a cheap CI environment for testing dbt changes against real-shaped data. Clones copy PII too, so the masking policies have to come with them.

Interview-ready answers

If asked: "Have you used Snowflake?"
"Not in production. My warehouse work is Oracle and PostgreSQL. I've studied how Snowflake separates storage from compute, and the parts that would be my job here, cost control and access policies, line up with work I already do: least-privilege service accounts, keeping secrets out of code, and controlling who sees student data."

If you've done the trial by then, add one sentence about what you built in it.

"How would you keep Snowflake costs under control?"
"Separate warehouses per workload so the bill shows who's spending, short auto-suspend, resource monitors with alerts before the limit, and a weekly look at metering history. Then fix the usual causes: sync frequency, dashboards left refreshing, full rebuilds that could be incremental."
"How would you handle PII in Snowflake?"
"Start with an inventory: which tables and columns hold student data. Tag them, attach masking policies to the tags, give every service its own user and a role that does only its job, and check that nothing is granted to PUBLIC. Then write a retention standard that accounts for Time Travel, Fail-safe and clones. And document it so analysts know why they see masked values."

Flashcards

What are the three layers of Snowflake?

Cloud services (brain: auth, optimizer, metadata), virtual warehouses (compute), and storage (micro-partitions in cloud object storage).

What is a credit, and how many does an X-Small use?

The unit of compute billing. X-Small uses 1 credit per hour, and each size up doubles it. Billing is per second with a 60-second minimum on each resume.

Why doesn't Snowflake need indexes?

It stores min/max metadata per column per micro-partition and skips (prunes) partitions that can't match the filter. Clustering keys help when natural ordering doesn't.

What's the difference between Time Travel and Fail-safe?

Time Travel (1 day by default, up to 90 on Enterprise) is self-service: query or undrop past data. Fail-safe is 7 more days that only Snowflake support can recover.

How do you mask a column for most users?

Create a masking policy (a CASE on the current role) and attach it to the column, or to a tag that's applied to the column.

Where do you look to explain a cost spike?

SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY for credits by warehouse, then QUERY_HISTORY (with query tags) to find the queries behind it.

What is a zero-copy clone good for?

Instant copies of a database or table for dev and CI testing. They share storage until changed. Remember they copy PII too.

What column type holds JSON?

VARIANT. Query with col:path.to.field::type and expand arrays with LATERAL FLATTEN.

Try it yourself in an evening

Snowflake offers a free 30-day trial with $400 in credits, and no credit card is needed. One evening with it lets you say "I've worked through it hands-on" truthfully.

  • Create an X-Small warehouse with AUTO_SUSPEND = 60.
  • Query the built-in SNOWFLAKE_SAMPLE_DATA.TPCH_SF1 tables and open the Query Profile. Find "partitions scanned".
  • Create two roles, a masking policy on a name column, and check what each role sees.
  • Drop a table, UNDROP it, then clone a database.
  • Load a small JSON file into a VARIANT column and query it with : paths and FLATTEN.
  • Check WAREHOUSE_METERING_HISTORY for what your evening cost. Account usage views can lag by up to a few hours.
