A. Background and walkthrough

A1. A pipeline you built and own

Strong answer: use CDWTool, in order: source → transport → destination → controls → failure modes → how you'd know. - Source: 14 student-level tables in Oracle, including student personal data. - Transport: Oracle Data Pump export, compressed, delivered to the Ministry (describe current delivery accurately; it was moving from SFTP to SharePoint in 2026), archived. - Controls: duplicate protection per reporting period, job history, SSO and privilege checks, a dedicated Ministry service account, secrets out of code. - What can go wrong: an export fails partway, the wrong period gets sent twice, credentials expire, the file is incomplete, someone without the right privilege runs it. - How you'd know: job history and status, duplicate check, row counts, and the Ministry's acceptance. - End with what you'd improve: an automated count check against the source, or an alert on failure.

Red flags: describing it only as "a .NET app." Not mentioning failure modes. Overstating scale.

B. SQL you write

B1. Latest pass per student

Strong answer:

-- Way 1: window function + QUALIFY (Snowflake)
SELECT *
FROM hall_passes
QUALIFY ROW_NUMBER() OVER (PARTITION BY student_id
                           ORDER BY created_at DESC, pass_id DESC) = 1;

-- Way 2: works everywhere
SELECT h.*
FROM hall_passes h
JOIN (SELECT student_id, MAX(created_at) AS max_created
      FROM hall_passes GROUP BY student_id) m
  ON m.student_id = h.student_id AND m.max_created = h.created_at;
  • Why the tiebreaker: two passes with the same timestamp make ROW_NUMBER arbitrary. Adding pass_id makes it deterministic.
  • Way 2 returns both rows on a tie. Mention it.
  • QUALIFY filters on window functions without a subquery. Oracle doesn't have it (you'd wrap in a subquery), but Snowflake does.

Red flags: using GROUP BY student_id and selecting other columns. Forgetting ties.

Study: Docs: Snowflake QUALIFY, ROW_NUMBER. Guide: dbt (dedupe in staging).

B2. Passes per school per local day

Strong answer:

WITH local_passes AS (
  SELECT h.school_id,
         CONVERT_TIMEZONE('UTC', s.timezone, h.created_at)::DATE AS local_day
  FROM hall_passes h
  JOIN schools s ON s.school_id = h.school_id
  WHERE h.created_at >= DATEADD(day, -9, CURRENT_TIMESTAMP())   -- pad for time zones
)
SELECT school_id, local_day, COUNT(*) AS passes
FROM local_passes
WHERE local_day >= DATEADD(day, -7, CURRENT_DATE)
GROUP BY school_id, local_day
ORDER BY school_id, local_day;
  • Convert to the school's time zone before taking the date. A pass at 7:30pm Pacific is already the next day in UTC.
  • Pad the UTC filter, then filter on the local date.
  • Bonus points:
  • Days with zero passes won't appear. Use a date spine if the dashboard needs zeros.
  • "Last 7 days" relative to whose today? Say it.

Red flags: created_at::DATE with no time-zone conversion.

Study: Docs: Snowflake CONVERT_TIMEZONE, TIMESTAMP_NTZ vs TIMESTAMP_TZ. Guide: Python (dates and time zones).

B3. 3+ tardies in any 7-day window

Strong answer:

SELECT a.student_id, a.tardy_date AS window_end, COUNT(*) AS tardies_in_window
FROM tardies a
JOIN tardies b
  ON b.student_id = a.student_id
 AND b.tardy_date BETWEEN DATEADD(day, -6, a.tardy_date) AND a.tardy_date
GROUP BY a.student_id, a.tardy_date
HAVING COUNT(*) >= 3;
  • A self-join counts each student's tardies in the 7 days ending on each tardy date.
  • Return DISTINCT student_id if they only want the list of students.
  • Alternative: a window function with a date-range frame. Snowflake supports interval-based RANGE frames, but check the docs before relying on it.
  • Questions to ask: "7-day window" means calendar days or school days? Do two tardies on the same day count twice?

Red flags: DATE_TRUNC('week') buckets. That misses a run of tardies that crosses a week boundary. Say why if you mention it.

Study: Docs: Snowflake window frames. Practice self-joins.

B4. Active schools with no passes in 14 days

Strong answer:

SELECT s.school_id, s.name
FROM schools s
WHERE s.is_active
  AND NOT EXISTS (
    SELECT 1 FROM hall_passes h
    WHERE h.school_id = s.school_id
      AND h.created_at >= DATEADD(day, -14, CURRENT_TIMESTAMP())
  );
  • NOT EXISTS is safe with nulls (compare C1).
  • Context points:
  • Summer break and holidays make "no passes" normal. Check the school calendar before flagging churn.
  • A school might use other features, not passes.
  • Ask Ted what "inactive" should mean.

Red flags: NOT IN against a column that could be null.

B5. Per-district rollup without double counting

Strong answer: aggregate each table to the district level separately, then join.

WITH st AS (
  SELECT sc.district_id, COUNT(*) AS active_students
  FROM students s JOIN schools sc ON sc.school_id = s.school_id
  WHERE s.is_active
  GROUP BY sc.district_id
),
sch AS (
  SELECT district_id, COUNT(*) AS schools
  FROM schools GROUP BY district_id
),
hp AS (
  SELECT sc.district_id, COUNT(*) AS passes_30d
  FROM hall_passes h JOIN schools sc ON sc.school_id = h.school_id
  WHERE h.created_at >= DATEADD(day, -30, CURRENT_TIMESTAMP())
  GROUP BY sc.district_id
)
SELECT d.district_id, d.name,
       COALESCE(st.active_students, 0) AS active_students,
       COALESCE(sch.schools, 0)        AS schools,
       COALESCE(hp.passes_30d, 0)      AS passes_30d,
       hp.passes_30d / NULLIF(st.active_students, 0) AS passes_per_student
FROM districts d
LEFT JOIN st  ON st.district_id  = d.district_id
LEFT JOIN sch ON sch.district_id = d.district_id
LEFT JOIN hp  ON hp.district_id  = d.district_id;
  • The trap: joining students and hall_passes in one query and counting multiplies the rows ("fan-out"). You'd get passes × students.
  • NULLIF avoids divide-by-zero.

Red flags: one big join with COUNT(*). COUNT(DISTINCT ...) everywhere as a band-aid. It can work for counts but hides the problem and breaks sums.

Study: Search "SQL join fan-out" / "chasm trap." This is the most common real-world reporting bug, and Ted will know it.

B6. Weekly active users with week-over-week change

Strong answer:

WITH wau AS (
  SELECT DATE_TRUNC('week', occurred_at) AS week_start,
         COUNT(DISTINCT user_id) AS wau
  FROM events
  GROUP BY 1
)
SELECT week_start, wau,
       LAG(wau) OVER (ORDER BY week_start) AS prev_wau,
       ROUND(100 * (wau - LAG(wau) OVER (ORDER BY week_start))
             / NULLIF(LAG(wau) OVER (ORDER BY week_start), 0), 1) AS pct_change
FROM wau
ORDER BY week_start;
  • Bonus points:
  • Week start depends on Snowflake's WEEK_START parameter. Say "I'd confirm which day weeks start on."
  • The current week is partial, so it looks like a drop. Exclude it or label it.
  • School holidays cause big swings. Compare to the same week last year.

Red flags: summing daily distinct users to get weekly (double counts people active on several days).

B7. Flatten JSON tags

Strong answer:

SELECT e.event_id,
       e.properties:device.os::STRING AS device_os,
       t.value::STRING                AS tag
FROM events e,
     LATERAL FLATTEN(input => e.properties:tags) t;
  • : walks into the VARIANT, . goes deeper, and ::STRING casts. Without the cast you get JSON-quoted values.
  • FLATTEN makes one row per array element.
  • Events with no tags disappear. Add OUTER => TRUE to keep them with a null tag.

Red flags: treating the JSON as a string and using LIKE.

Study: Guide: Snowflake "Loading and JSON." Docs: FLATTEN, semi-structured data.

C. SQL you debug

C1. NOT IN returns nothing

Strong answer: withdrawals.student_id contains at least one NULL. x NOT IN (..., NULL) evaluates to unknown for every row, so nothing comes back. Fix:

SELECT s.student_id FROM students s
WHERE NOT EXISTS (SELECT 1 FROM withdrawals w WHERE w.student_id = s.student_id);

Then ask why withdrawals has null student IDs. That's a data-quality problem worth a not_null test.

Study: "NOT IN NULL trap." Same behaviour in Oracle.

C2. LEFT JOIN that acts like an INNER JOIN

Strong answer: the WHERE h.created_at >= ... filter throws away the rows where h is null (schools with no passes), turning the LEFT JOIN into an inner join. Move the condition into the ON:

SELECT s.name, COUNT(h.pass_id) AS passes
FROM schools s
LEFT JOIN hall_passes h
  ON h.school_id = s.school_id
 AND h.created_at >= DATEADD(day, -7, CURRENT_DATE)
GROUP BY s.name;
  • Also: COUNT(h.pass_id) is right (it counts 0 for no match). COUNT(*) would count 1.
  • Grouping by name merges two schools with the same name. Group by school_id.

C3. Missing October 31

Strong answer: '2026-10-31' means 2026-10-31 00:00:00, so everything after midnight on the 31st is excluded. Use a half-open range:

WHERE created_at >= '2026-10-01' AND created_at < '2026-11-01'
  • Second issue: those are UTC boundaries. A school's October in local time is shifted by several hours. Say whose month it is.

C4. COUNT(*) vs COUNT(ended_at)

Strong answer: - COUNT(column) skips nulls. The difference is the number of passes with no ended_at: still open, or never closed properly (a real product question, since passes that never end distort duration reports). - "How many passes were created" is COUNT(*) (or COUNT(pass_id), since the key is never null).

C5. Two dashboards disagree on active students

Strong answer: check in this order. 1. Definition: is_active flag vs "had activity in 30 days" vs "rostered this year." Different filters are the usual cause. 2. Source: raw table vs a mart, or different models. 3. Timing: one is cached or stale. Check freshness and Metabase caching. 4. Joins: fan-out in one of them. 5. Duplicates: the same student at two schools after a transfer, or duplicate SIS records. 6. Time zone and date boundaries.

Fix: one agreed definition, one tested model, both dashboards point at it, and the definition is documented.

Red flags: "I'd just pick the one that looks right."

D. "AI wrote this" review tests

D1. The ARR query

Problems: 1. Fan-out: the join to schools repeats each contract once per school, so ARR is multiplied by the number of schools. This is the biggest bug. 2. LEFT JOIN made inner: s.is_active = TRUE in WHERE drops districts with no active school. 3. Wrong logic for ARR over time: grouping by the month the contract started gives new bookings by month, not ARR. ARR in a month = contracts active in that month (start ≤ month end, and end ≥ month end or open). 4. Current status used for history: status = 'active' is today's status, so churned contracts vanish from past months and history rewrites itself. 5. Currency: USD and CAD summed together. 6. Grouping by name: two districts with the same name merge. Group by district_id. 7. No time range: months with no new contracts vanish (no month spine).

Better version (sketch):

WITH months AS (
  SELECT DATEADD(month, ROW_NUMBER() OVER (ORDER BY SEQ4()) - 1, '2024-01-01'::DATE) AS month_start
  FROM TABLE(GENERATOR(ROWCOUNT => 36))
)
SELECT c.district_id, m.month_start, c.currency,
       SUM(c.annual_value) AS arr
FROM months m
JOIN contracts c
  ON c.start_date <= LAST_DAY(m.month_start)
 AND (c.end_date IS NULL OR c.end_date >= LAST_DAY(m.month_start))
WHERE c.status <> 'void'                -- exclude contracts that never happened
GROUP BY 1, 2, 3;
  • Then convert currency with a rate table, or report per currency.
  • Most important: before trusting any of it, agree the ARR definition with Ted and Finance.

What they're scoring: you found the fan-out and the "bookings, not ARR" logic error, and you didn't just tidy the syntax.

Study: B5 (fan-out), J1 (ARR definition). Docs: Snowflake GENERATOR.

D2. The dbt incremental model

Problems: 1. created_at instead of updated_at: a pass that ends, or changes status, after it's loaded is never updated. Durations and statuses go stale. 2. No lookback window: late-arriving rows with a timestamp slightly older than the max are skipped forever. Use something like updated_at > (select max(updated_at) - interval '3 days' ...). The unique_key merge handles the overlap. 3. select * from the source: - Schema drift: a new column can break the model or silently add PII. - No renaming or casting: this should be a staging model. - PII flows straight through. 4. Hard deletes are never handled (see F2). 5. No tests and no docs. 6. No plan for logic changes: changing an incremental model needs a --full-refresh. Consider on_schema_change.

Before approving, ask for: - Explicit columns and staging conventions. - Tests: unique and not_null on pass_id, relationships, accepted_values on status. - Source freshness. - A CI run. - A note on how deletes are handled. - Proof it matches a full rebuild on a sample (counts compared).

Study: Guide: dbt (materializations, tests, review workflow). Docs: dbt incremental models, is_incremental, on_schema_change.

D3. The Python loader

Problems (roughly by severity): 1. Secrets in code: an API token and a Snowflake password hard-coded. If this was ever committed, rotate both now. 2. admin user: the loader should be its own service user, with a role that can only write RAW, and key-pair auth. 3. SQL built with f-strings: injection risk, and it breaks on O'Brien. Use bound parameters, or bulk load. 4. Student names landing in raw: ask whether it's needed at all (data minimization), and if so, mask it. 5. No pagination: only the first page is ever loaded. 6. No timeout, no status check: requests.get can hang, and a 500 error page gets parsed as JSON. 7. except Exception: pass in while True: failures are swallowed silently, and the loop hammers the API with no sleep. 8. Not incremental and not idempotent: it always pulls since 2026-01-01 and inserts again, duplicating rows every loop. 9. datetime.utcnow(): deprecated in 3.12, and naive. Use datetime.now(timezone.utc). 10. print instead of logging: no counts in or out. 11. Row-by-row inserts: slow. Stage and bulk load, then MERGE.

What they're scoring: you see the security problems first (secrets, admin, injection, PII), then reliability.

Study: Guide: Python (calling APIs, talking to databases, pipeline habits).

D4. "Add indexes"

Strong answer: - That's wrong for Snowflake. Standard tables have no indexes. Snowflake prunes micro-partitions using min/max metadata. (Niche features like search optimization and hybrid tables exist, but they aren't the answer to a cost spike.) - Then investigate properly: - SNOWFLAKE.ACCOUNT_USAGE.METERING_DAILY_HISTORY: is the increase in warehouses or serverless features? - WAREHOUSE_METERING_HISTORY by warehouse and day: which one, and when did it start? - QUERY_HISTORY: the most expensive queries, by user and warehouse. - Recent changes: warehouse size, auto-suspend setting, sync frequency, new dashboards. - The point: AI is useful for drafting the queries, but a confident, unverified diagnosis gets checked against the platform's own usage data.

Study: Guide: Snowflake (no indexes / pruning; warehouses and cost).

E. Data modelling

E1. Hall-pass reporting model

Strong answer: - fct_hall_passes, grain: one row per pass. - Keys: pass_id, student_key, school_key, staff_key, date_key. - Times: created_at (UTC), local date, ended_at. - Measures and attributes: duration in minutes, pass_type, status. - Dimensions: - dim_school: district, state or province, time zone, plan. - dim_student: grade, school, active flag, no names. - dim_staff, dim_date (with school-year and term). - Pass type, if it has attributes. - PII: names, emails and SIS IDs live in a restricted table or schema (or are masked), and join only for roles that need them. - For dashboards: a pre-aggregated fct_hall_passes_daily (school × local day × pass type) keeps Metabase fast and cheap. - Say the grain out loud first. That's what interviewers listen for.

Study: Kimball star schema basics: grain, facts, dimensions. Guide: dbt (marts).

E2. Plan changes mid-year

Strong answer: - This is a type 2 slowly changing dimension: keep a row per version, with valid_from and valid_to. - In dbt, a snapshot on the subscriptions table builds this automatically (dbt_valid_from, dbt_valid_to). - Revenue facts join on fact_date BETWEEN valid_from AND COALESCE(valid_to, '9999-12-31'). - Better still, if billing has a subscription-change history at the source, model that directly instead of snapshotting.

Red flags: overwriting the plan column (history lost), or copying the plan onto every fact row by hand.

Study: Guide: dbt (snapshots). "Kimball SCD type 2."

E3. Nested arrays in MongoDB documents

Strong answer: - Tables: - Parent: stg_students, one row per student, scalar fields only. - Children: stg_student_guardians and stg_student_classes, one row per array element. They carry student_id plus either the element's own ID or its array index. - Built with LATERAL FLATTEN in staging. Keep the raw VARIANT in RAW. - Decisions to make: - Keys: what identifies an array element? If it has no ID, the index changes when the order changes. - History: do we need to know when a guardian was removed? - Empty or missing arrays: use OUTER => TRUE. - PII: guardian names, phones and emails are restricted data. - Deeper nesting. - Say that you'd look at real documents first, because Mongo collections often hold several shapes over time.

Study: Guide: Snowflake (loading and JSON).

E4. Event model for the new platform

Ask for in every event: - event_id (unique, for de-duplication). - event_name from an agreed list, with a naming convention (hall_pass_created, object_action). - occurred_at in UTC, plus received_at (server time). - Who and where: user_id (pseudonymous), user_role (student, teacher, admin), school_id, district_id. - platform, app_version, schema_version. - Typed, documented properties.

Push back on: - PII in properties: names, free-text notes, emails. Use IDs. - Vague events: "button_clicked". - Events no one will use: every event needs a question it answers and an owner. - Changing meanings without a version bump.

Process: a tracking plan in git, reviewed like code, with tests in the pipeline that reject unknown events. The tenancy keys (district_id) also make the 90-day per-district deletion possible.

Connection: Paolo built Segment/Mixpanel event pipelines at Metalab. Ask him how they'd like to approach it.

E5. Reporting across legacy and new platforms during migration

Strong answer: - Separate staging models per platform, feeding one conformed model with a source_platform column. - An ID crosswalk table (legacy ID → new ID) per entity. - A migration status table per customer, with a cutover date. For each customer and date, decide which platform is the source of truth, so the overlap period isn't double counted. - Reconciliation tests: counts and totals per school before and after cutover. - Dashboards that show the platform split while the migration is underway.

Your evidence: the VIU legacy modernization (about 90 apps, conversion guide, data and sign-on kept intact).

F. Pipelines and ingestion

F1. Stitch says success, numbers look low

Strong answer, in order: 1. Freshness: MAX(_sdc_batched_at) and row counts per day in RAW, compared with a normal day. 2. Stitch: rows replicated per table, any skipped tables, replication key or bookmark problems. 3. The source itself: was there an app outage or a holiday? Check with Product or SRE. 4. dbt: did the run finish, and did tests fail? 5. Definitions and time: is "yesterday" UTC or local? Metabase cache? Dashboard filters? 6. Tell people early: "Yesterday's numbers look low; I'm investigating; next update at 11." 7. Afterwards: add a freshness test and a volume alert so the pipeline tells you next time, not a stakeholder.

Red flags: jumping to "rerun everything." Not telling stakeholders.

F2. Hard deletes with incremental loads

Strong answer: - The gap: an incremental load based on updated_at only sees rows that still exist. A deleted document never shows up again, so it stays in the warehouse forever. - Why it matters at Minga: - Wrong numbers: deleted students or passes still counted. - Privacy commitments: Minga promises to delete or de-identify a district's data within 90 days of contract end, and students removed through SIS syncs should go too. Leftover copies in the warehouse break that promise. - Fixes: - Log-based or change-stream replication (the MongoDB oplog or change streams) that captures delete events, if the loader supports it. - Soft deletes in the app (deleted_at). - Periodic key reconciliation: compare the full list of IDs in the source with the warehouse, and mark missing ones as deleted. - Plus a documented deletion process that reaches every copy (see G4).

Study: Docs: Stitch replication methods (key-based incremental vs log-based). Search "hard deletes incremental ELT."

F3. Idempotency

Strong answer: - Definition: running a job twice gives the same result as running it once. - How: - MERGE on a unique key. - Delete-and-insert by partition (replace a whole day). - Load to staging and swap. - Use the run's logical date, not now(), so a rerun of Tuesday processes Tuesday. - Why: retries, backfills and overlapping incremental windows are routine, so every job must be safe to repeat. - Your example: CDWTool's per-period duplicate protection.

Study: Guide: Airflow (reliability), Python (pipeline habits).

F4. Schema drift

Strong answer: - New field: loaders like Stitch usually add a column automatically. Fine in RAW. It shouldn't silently appear in marts (explicit columns in staging prevent that). - Type change (number → string): Stitch typically splits it into an extra column with a type suffix rather than failing. Check the Stitch docs for the exact naming. Staging models that cast explicitly will then show nulls or fail. - Desired behaviour: - RAW accepts anything (VARIANT is fine). - Staging casts explicitly and fails loudly through tests or dbt model contracts. - An alert tells you. - You talk to the product team, ideally before the change, through the event and data contract process (E4).

F5. Backfilling two years

Strong answer: - Confirm the source still has two years of history (app database, exports, backups) and that the shape hasn't changed over time. - Load into a separate table, in chunks (by month), with each chunk idempotent. - Size the warehouse up temporarily, with a resource monitor on it. - Reconcile counts and totals per month against the source. - Then swap it in, using a zero-copy clone of the current table as a rollback point. - Don't disturb the daily loads. - Tell people that historical numbers will change, and when.

G. Snowflake

G1. Bill up 60%

Strong answer: - ACCOUNT_USAGE.METERING_DAILY_HISTORY: which service (warehouses, or serverless like automatic clustering and Snowpipe)? - WAREHOUSE_METERING_HISTORY: which warehouse, and from what date? - QUERY_HISTORY (with query tags if they're set): which users, tools and queries? - Common causes: a warehouse resized and never sized back, auto-suspend raised, a new or more frequent sync, a dashboard auto-refreshing, a full rebuild that used to be incremental, a runaway query. - Storage is billed separately: check for Time Travel growth. - Account usage views can lag by up to a few hours. - Then fix the cause, and prevent it: resource monitors and budgets, a warehouse per workload, and query tags on dbt and Metabase.

Study: Guide: Snowflake (warehouses and cost). Docs: resource monitors, ACCOUNT_USAGE views.

G2. Role design

Strong answer:

Role Can do Warehouse
LOADER (Stitch / custom loaders) Write RAW only LOAD_WH
TRANSFORMER (dbt) Read RAW, write STAGING / MARTS TRANSFORM_WH
REPORTER (Metabase service user) Read MARTS, PII masked BI_WH
ANALYST (RevOps etc.) Read MARTS, write own sandbox schema, PII masked ANALYST_WH
PII_READER Unmasked student fields, granted narrowly and reviewed (added on top)
Data engineer (you) Builds everything; ACCOUNTADMIN only as break-glass with MFA
  • Service users use key-pair auth, not passwords.
  • Grant future grants so new tables follow the rules.
  • Nothing granted to PUBLIC.
  • Review grants each quarter.
  • Who sees names: only PII_READER, through masking policies.

Study: Guide: Snowflake (access and PII). Docs: Snowflake access control, functional vs access roles.

G3. Masking policy SQL

Strong answer:

CREATE MASKING POLICY governance.policies.mask_student_name
  AS (val STRING) RETURNS STRING ->
  CASE
    WHEN IS_ROLE_IN_SESSION('PII_READER') THEN val
    ELSE '***'
  END;

ALTER TABLE analytics.marts.dim_students
  MODIFY COLUMN last_name SET MASKING POLICY governance.policies.mask_student_name;
  • Needs Enterprise edition or higher. Ask which edition they're on.
  • IS_ROLE_IN_SESSION respects role hierarchy. CURRENT_ROLE() = 'PII_READER' only matches that exact role.
  • At scale: attach the policy to a tag (pii = 'student_name') and tag the columns, so new columns get masked by tagging.

Study: Docs: Snowflake masking policies, tag-based masking.

G4. "Deleted" isn't gone yet

Strong answer: - Time Travel: dropped or deleted data can be recovered for the retention period (1 day by default, up to 90 on Enterprise). - Fail-safe: 7 more days for permanent tables, recoverable only by Snowflake support. You can't purge it early. - Other copies: - Clones made earlier still hold the data. - Copies in other schemas, dev and CI schemas, analyst sandboxes. - Metabase caches and CSV downloads. - Exports, Stitch staging, and any backups. - What to do: - Keep an inventory of where student data lives. - Use shorter DATA_RETENTION_TIME_IN_DAYS on PII tables (or transient tables, which skip Fail-safe, where it's safe). - De-identify where the policy allows. - Log each deletion with dates, so you can show the 90-day commitment was met, counting Time Travel and Fail-safe.

Study: Guide: Snowflake (Time Travel and clones).

G5. Warehouse that never sleeps

Strong answer: - Why: every query resets the auto-suspend timer. Loads every 30 minutes, plus dashboards refreshing every few minutes, can keep a warehouse running all day and night. Each resume also bills at least 60 seconds. - Fixes: - Separate warehouses for loading and BI, so you can see who's spending. - Short auto-suspend (about 60 seconds). - Sync only as often as the business needs: hourly or nightly is usually fine for revenue data. - Metabase caching and less frequent refresh. - Build marts as tables, so dashboard queries are cheap.

H. dbt

H1. Day-one tests

Strong answer: - fct_hall_passes: - unique and not_null on pass_id. - not_null on school_id, student_id, created_at. - relationships to dim_school and dim_student. - accepted_values on status and pass_type. - A custom test: ended_at >= created_at when ended_at is not null. - Source freshness on the raw table. - dim_students: - unique and not_null on student_id. - relationships to dim_school. - accepted_values or a range check on grade. - Maybe uniqueness of (school_id, sis_id). - Approach: start with the tests that would have caught real past incidents (ask Ted what went wrong before), and don't drown in low-value tests.

Study: Guide: dbt (tests and freshness).

H2. Layers

Strong answer: - Staging (stg_): one model per source table. Rename, cast, light cleaning. No joins. The only models that read source(). - Intermediate (int_): joins and business logic building blocks. Not exposed to BI. - Marts (fct_ / dim_): business-facing, documented, tested, what Metabase and analysts use. - Why: each rule lives in one place, and analysts know where to build.

H3. An analyst's change reaching production

Strong answer: 1. Branch. 2. Build in their own dev schema (dbt build against the dev target). 3. Open a PR using a template: what changed, why, how it was tested. 4. CI (slim CI): build only modified models and what depends on them (state:modified+, with --defer to production for the rest), plus tests. 5. Review: you check the logic, CI checks the mechanics. 6. Merge. 7. The production job deploys. 8. Docs are updated.

Make the path fast so analysts don't route around it.

Study: Guide: dbt (the review workflow).

H4. Incremental models

Strong answer: - When: large, append-heavy tables (events, passes) where a full rebuild is slow or expensive. - Risks: - Late-arriving data is missed without a lookback window. - Deletes aren't handled. - A logic change needs a --full-refresh. - The incremental table can drift from what a full rebuild would produce, so schedule a periodic full refresh or a comparison. - Don't make small tables incremental. The complexity isn't worth it.

J. RevOps and stakeholders

J1. ARR, churn, NRR

Strong answer: - ARR (annual recurring revenue): the annualized value of active recurring subscriptions at a point in time. - Include: recurring subscription fees, net of recurring discounts. - Exclude: one-time fees (implementation, training, hardware), and usage that isn't contracted. - Churn: - Logo churn: customers lost ÷ customers at the start. - Revenue churn: ARR lost ÷ starting ARR. - NRR (net revenue retention): for customers who existed at the start of the period, (starting ARR + expansion − contraction − churn) ÷ starting ARR. Usually measured over 12 months. New customers are excluded. - GRR (gross revenue retention): the same, without expansion. It can't exceed 100%. - K-12 point: renewals cluster around the school fiscal year (often July 1), so monthly churn is lumpy. Annual views matter more.

Study: search "SaaS metrics ARR NRR GRR definitions." Ted lives in these. Get the formulas right.

N. AI in practice [Human driving]

N1. Review checklist for AI-written SQL

Strong answer: 1. Grain: what is one row? Is that what was asked? 2. Joins: any fan-out? Are LEFT JOINs still left (no WHERE on the right table)? 3. Filters and dates: half-open ranges, time zones, current vs historical status. 4. Nulls: NOT IN, COUNT(col), division by zero. 5. Definitions: does it match the agreed metric definition? 6. Security: no PII in marts, no secrets, parameters not string-building. 7. Tests: unique and not-null on the grain key, plus a test for the specific logic. 8. Reconciliation: compare the totals with a known number or the source. 9. Cost: full scans of big tables, incremental where it matters. 10. Explainability: can the reviewer explain every line? If not, it doesn't merge.

N2. Narrating "tardies per student per week" with Claude

Strong answer (talk while you do it): 1. Write the spec first: - Grain is student × week. - Which day does a week start (check Snowflake's WEEK_START)? - School time zone? (tardy_date is already a date, so mostly fine.) - Do we need weeks with zero tardies? - What happens when a student transfers mid-week? 2. Give Claude the schema and the spec, not just the sentence. 3. Read the SQL line by line and say what each part does. 4. Run it on a small sample with a known answer: pick one student and count by hand. 5. Check edge cases: week boundaries, duplicates, transfers. 6. Add tests, and compare the total with COUNT(*) from tardies.

What they're scoring: you drive with a spec and verification, and you say "I don't trust this until..." out loud.

N3. Spotting confidently wrong AI answers

Strong answer: - Warning signs: - Functions or columns that don't exist. - Syntax from the wrong database (PostgreSQL or Oracle syntax in Snowflake). - Advice from another platform (indexes in Snowflake, as in D4). - Numbers with no source. - Too-neat explanations. - How to verify: - Run it. - Check the official docs. - Reconcile against the source. - Test small cases with known answers. - Ask it for the doc reference, then actually read it.

N4. Explain the query without AI

Strong answer: - What it does: per school, it counts distinct students who have any pass, all time, and divides all passes by that number. - Issues: 1. The denominator only includes students who used a pass at least once. Students with zero passes are missing, so it's "passes per student who used passes," not per enrolled student. Use active enrolment from students if that's the question. 2. No date range: it's all time, so it mixes school years. 3. Division behaviour depends on the database. In PostgreSQL or SQL Server, integer ÷ integer truncates (7/2 = 3). Snowflake returns a decimal. Mention this; it shows you know platforms differ. 4. Transfers: school_id is the pass's school, so a student who transferred counts at both schools. Probably fine, but say it.

Scoring: a plain explanation first, then the denominator issue. That's the one they're looking for.
