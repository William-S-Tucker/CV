Snowflake Field Guide

Snowflake is the cloud data warehouse Minga already runs on. This guide explains it in terms of the Oracle work you already know, then covers the two things the posting cares about most: cost and student data.

The one-minute version

  • A SQL database delivered as a service. No servers, tablespaces, indexes, or patching. You write SQL and it runs.
  • Storage and compute are separate. One copy of the data sits in cloud storage. Compute comes from virtual warehouses, which are clusters you switch on and off.
  • You pay for storage (cheap) and for every second a warehouse is running (where the money goes). Costs come from warehouses left running.
  • Access is role-based, like Oracle grants. Enterprise edition adds column masking and row-level policies, which is how you'd protect student PII.
Where it sits at Minga

The posting names the stack: Stitch pulls data out of the product and business tools, loads it into Snowflake, and analysts read it through Metabase. Snowflake is the centre: everything lands there, gets transformed there, and gets queried there.

How it's built

Snowflake has three layers. Once you see them, most of its behaviour (and its bill) makes sense.

  • Cloud services is the brain: authentication, the optimizer, metadata, and security policies. Mostly free (it's billed only if it goes over 10% of your daily warehouse usage).
  • Virtual warehouses are the muscle. They start in seconds, suspend themselves when idle, and come in T-shirt sizes.
  • Storage is the memory. Tables are split into compressed, column-oriented files called micro-partitions. You never manage files.

Snowflake runs on AWS, Azure, or Google Cloud. You pick a cloud and region when the account is created, but you never touch that cloud directly.

Oracle to Snowflake, side by side

Most of your SQL carries over. Snowflake supports NVL, DECODE, MERGE, CONNECT BY, analytic functions, and CTEs, and unquoted identifiers default to uppercase like Oracle. The differences are in everything around the SQL.

Keep it accurate

This table is for learning. In the interview, your claim is "my warehouse work is Oracle and PostgreSQL." Don't say Oracle experience is Snowflake experience. Saying "I understand how my Oracle work maps onto it" is fine.

Warehouses and cost

The posting says: "Keep Snowflake and pipeline costs proportional to usage, and know exactly why when they aren't." That's all about warehouses.

SizeCredits per hourRule of thumb
X-Small1Most loading and BI at Minga's scale
Small2Typical dbt runs
Medium4Heavy transforms, big backfills
Large8Rarely needed at this size of company
X-Large and up16, 32 …Each size doubles the cost and roughly the speed

A credit costs roughly $2 to $4 USD depending on edition, cloud region, and contract. Billing is per second, with a 60-second minimum every time a warehouse resumes. Two settings control most of the bill:

  • AUTO_SUSPEND = 60 turns the warehouse off after 60 idle seconds.
  • AUTO_RESUME = TRUE turns it back on when a query arrives.

Where surprise bills come from

  • Frequent loads. If Stitch syncs every 30 minutes, it wakes the loading warehouse 48 times a day, and each wake-up bills at least 60 seconds. Sync frequency is a cost setting.
  • Dashboards on auto-refresh. A Metabase dashboard left open on a wall screen keeps the BI warehouse awake all day.
  • Oversized warehouses. Someone bumped a warehouse to Large for one backfill and never set it back.
  • Full rebuilds. dbt rebuilding big tables from scratch every hour when an incremental model would do.

How you find out why

-- Credits per warehouse per day, last 30 days
select warehouse_name,
       date_trunc('day', start_time) as day,
       sum(credits_used)              as credits
from snowflake.account_usage.warehouse_metering_history
where start_time >= dateadd('day', -30, current_timestamp())
group by 1, 2
order by 2, 3 desc;
  • One warehouse per workload (loading, transforming, BI), so the bill already tells you who spent it.
  • Query tags (ALTER SESSION SET QUERY_TAG = 'dbt:nightly') to attribute spend inside a warehouse. dbt can set these for you.
  • Resource monitors: a monthly credit quota per warehouse that notifies you at, say, 80% and can suspend the warehouse at 100%.
  • The result cache: if someone reruns an identical query within 24 hours and the data hasn't changed, Snowflake returns the cached result without starting a warehouse. That's free.
No indexes: how queries stay fast

Snowflake stores the minimum and maximum value of every column for every micro-partition. When a query filters, it skips any partition whose range can't contain a match. This is called pruning, and it does the job indexes do in Oracle.

Pruning works well when you filter on a column that follows load order, like dates. If you filter on something scattered (a school ID that appears in every partition), nothing gets skipped. For very large tables you can add a clustering key so Snowflake keeps rows with similar values together. That re-sorting runs in the background and costs credits, so only use it when the Query Profile shows poor pruning on a big table.

Loading data, and JSON

Snowflake's own loading tools are stages (an internal area, or an S3/Azure/GCS bucket) plus COPY INTO, and Snowpipe for loading files as they arrive. At Minga, Stitch handles this. A few Stitch details worth knowing before you're asked to "harden or replace" it:

  • Stitch usually writes each source into its own schema in a raw database and adds metadata columns such as _sdc_batched_at and _sdc_extracted_at. Those are your freshness signal.
  • It replicates tables by key-based incremental (an updated_at column), log-based (database change logs), or full table. Hard deletes in the source can be missed with key-based incremental, so a student record removed in the product can survive in Snowflake. That matters for retention rules.
  • When a source column changes type, Stitch can split it into new columns with a type suffix. Staging models in dbt are where you clean that up.
  • Common replacements are Fivetran and Airbyte. Writing custom loaders in Python is another option.

Product event data usually arrives as JSON. Snowflake keeps it in a VARIANT column and you query it with a path syntax:

select
  payload:student_id::number      as student_id,
  payload:pass.type::string       as pass_type,
  f.value:name::string            as tag_name
from raw.app.events,
     lateral flatten(input => payload:tags) f   -- one row per tag in the JSON array
where payload:event_type::string = 'pass_started';

This connects to the posting's "analytics event model for the new platform": you'll help decide what those JSON events look like before they're ever written.

Access control and student PII

This is the part of the job closest to what you already do. The posting says it twice: "We hold student-level data and we treat it that way."

Roles

Snowflake ships with system roles. ACCOUNTADMIN is the top and should belong to very few people, with MFA on. SECURITYADMIN manages grants, SYSADMIN owns databases and warehouses, USERADMIN creates users, and PUBLIC is granted to everyone. Anything granted to PUBLIC is a red flag. Below those you design your own roles, one per job:

Masking and row policies

A masking policy is a function attached to a column. Every query runs through it, so it works the same in Metabase, a worksheet, or a dbt model.

create masking policy pii_string as (val string) returns string ->
  case when is_role_in_session('PII_READER') then val
       else '****'
  end;

alter table analytics.marts.dim_students
  modify column student_name set masking policy pii_string;
  • Row access policies filter rows by role. For example, a CX role only sees schools in the region it supports. This is like Oracle VPD.
  • Tag-based masking: tag columns as pii = 'name' or pii = 'email' and attach the policy to the tag. New PII columns are protected as soon as they're tagged.
  • ACCESS_HISTORY records which columns each query read, so you can answer "who looked at student data last month?"
  • Masking, row access policies, and access history need Enterprise edition or higher. Ask which edition Minga is on.

Secrets and service accounts

Service users should sign in with key-pair authentication (or OAuth), not passwords. Snowflake has been phasing out password-only sign-in. This is the same instinct as moving CDWTool onto a dedicated Ministry service account and getting secrets out of the repo, and that's a real story you can tell.

Retention

Deleting student data isn't instant in Snowflake. Deleted rows stay recoverable through Time Travel for the table's retention period, then sit in Fail-safe for 7 more days, where only Snowflake support can recover them. A retention standard has to account for both. It also has to cover copies in Metabase caches and in any clones.

Time Travel and zero-copy clones
-- What did this table look like an hour ago?
select * from marts.fct_hall_passes_daily at(offset => -3600);

-- Someone dropped it by mistake
undrop table marts.fct_hall_passes_daily;

-- A full copy of production for testing, created in seconds, no extra storage until it changes
create database analytics_ci clone analytics;
  • Time Travel retention defaults to 1 day. Enterprise edition allows up to 90. Longer retention means more storage cost and longer-lived copies of PII.
  • Zero-copy clones share the original's micro-partitions and only store what changes afterwards. They make a cheap CI environment for testing dbt changes against real-shaped data. Clones copy PII too, so the masking policies have to come with them.

Flashcards
What are the three layers of Snowflake?

Cloud services (brain: auth, optimizer, metadata), virtual warehouses (compute), and storage (micro-partitions in cloud object storage).

What is a credit, and how many does an X-Small use?

The unit of compute billing. X-Small uses 1 credit per hour, and each size up doubles it. Billing is per second with a 60-second minimum on each resume.

Why doesn't Snowflake need indexes?

It stores min/max metadata per column per micro-partition and skips (prunes) partitions that can't match the filter. Clustering keys help when natural ordering doesn't.

What's the difference between Time Travel and Fail-safe?

Time Travel (1 day by default, up to 90 on Enterprise) is self-service: query or undrop past data. Fail-safe is 7 more days that only Snowflake support can recover.

How do you mask a column for most users?

Create a masking policy (a CASE on the current role) and attach it to the column, or to a tag that's applied to the column.

Where do you look to explain a cost spike?

SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY for credits by warehouse, then QUERY_HISTORY (with query tags) to find the queries behind it.

What is a zero-copy clone good for?

Instant copies of a database or table for dev and CI testing. They share storage until changed. Remember they copy PII too.

What column type holds JSON?

VARIANT. Query with col:path.to.field::type and expand arrays with LATERAL FLATTEN.

Try it yourself in an evening

Snowflake offers a free 30-day trial with $400 in credits, and no credit card is needed. One evening with it lets you say "I've worked through it hands-on" truthfully.

  • Create an X-Small warehouse with AUTO_SUSPEND = 60.
  • Query the built-in SNOWFLAKE_SAMPLE_DATA.TPCH_SF1 tables and open the Query Profile. Find "partitions scanned".
  • Create two roles, a masking policy on a name column, and check what each role sees.
  • Drop a table, UNDROP it, then clone a database.
  • Load a small JSON file into a VARIANT column and query it with : paths and FLATTEN.
  • Check WAREHOUSE_METERING_HISTORY for what your evening cost. Account usage views can lag by up to a few hours.

dbt Field Guide

dbt is the "modelling layer" the posting wants you to introduce. It's SQL in version control, with tests and code review, and it runs inside Snowflake. That's very close to how you already work, which makes it your best bridge in the interview.

The one-minute version

  • dbt (data build tool) handles the T in ELT. Stitch extracts and loads raw data. dbt transforms it into clean tables people can trust.
  • You write each table as a SELECT statement in a .sql file. dbt wraps it in CREATE TABLE/VIEW AS and runs it in Snowflake.
  • Models refer to each other with ref(). dbt uses that to work out the run order, so you never write a dependency list by hand.
  • Tests (unique, not null, valid values, relationships, freshness) run after each build. The whole project lives in git and goes through pull requests like any other code.
  • dbt doesn't move data and doesn't need its own server for the data. All the compute happens in Snowflake.
Where it sits at Minga

The posting: "Introduce and own a modelling layer (dbt or equivalent) with versioning, tests and review that our RevOps analysts can build against without slowing down." Today there isn't one. Raw Stitch tables go more or less straight to Metabase, with the logic buried in dashboard queries.

What a model is

A model is one .sql file containing one SELECT. The file name becomes the table or view name. Here's a staging model over an illustrative raw table:

models/staging/app/stg_app__hall_passes.sql

with source as (
    select * from {{ source('app', 'hall_passes') }}
),

renamed as (
    select
        id                          as pass_id,
        school_id,
        student_id,
        lower(status)               as status,
        started_at::timestamp_ntz   as started_at,
        ended_at::timestamp_ntz     as ended_at,
        _sdc_batched_at             as loaded_at
    from source
)

select * from renamed

The {{ }} parts are Jinja, a templating language. When you run dbt, it compiles the file into plain SQL for Snowflake:

create or replace view analytics.staging.stg_app__hall_passes as (
    with source as (
        select * from raw.app.hall_passes
    ),
    ...
);

That's the core idea. You write SELECT, and dbt handles the DDL, the schema names, and the environment (your dev schema or production).

ref() and the dependency graph

Instead of hard-coding table names, a model says {{ ref('stg_app__schools') }}. That does two things: it points at the right schema for the current environment, and it tells dbt "this model depends on that one". dbt collects every ref() and source() into a graph and runs models in order.

Staging, intermediate, marts

The convention dbt Labs recommends, and the one most teams follow:

LayerWhat goes in itUsually built as
Staging stg_One model per raw table. Rename, cast types, fix obvious mess. No joins, no business logic. The only layer that reads source().Views
Intermediate int_Joins and business logic that's reused, kept out of sight of analysts.Views or ephemeral
Marts fct_ / dim_Facts (events, things that happen: passes, behaviour entries, invoices) and dimensions (things: schools, districts, accounts). This is what Metabase and analysts read.Tables or incremental

Think of it like your Oracle reporting work: raw extracts, then cleaned views, then the reporting tables people query. The difference is that every step is a file in git with tests attached.

Materializations

A model's materialization decides what dbt builds in Snowflake. You set it in the model or for a whole folder in dbt_project.yml.

TypeWhat it createsUse when
viewA view. Nothing stored. Computed when queried.Staging. Cheap to build, light to query.
tableA full table, rebuilt from scratch every runMarts that are small or medium sized
incrementalA table where each run only processes new or changed rowsBig event tables. This is a major cost lever.
ephemeralNothing. Inlined as a CTE into models that use it.Small helper logic

models/marts/fct_hall_passes.sql (incremental)

{{ config(materialized='incremental', unique_key='pass_id') }}

select * from {{ ref('stg_app__hall_passes') }}

{% if is_incremental() %}
  -- only on later runs: rows newer than what's already in this table
  where loaded_at > (select max(loaded_at) from {{ this }})
{% endif %}

On the first run, dbt builds the whole table. After that it merges only new rows, using unique_key to update rows that changed. dbt build --full-refresh rebuilds it from scratch when the logic changes.

Tests and freshness

Tests are declared in YAML next to the models. Each one compiles to a query that returns the rows that break the rule. Zero rows means it passes.

models/staging/app/_app__models.yml

models:
  - name: stg_app__hall_passes
    description: One row per hall pass issued in the Minga app.
    columns:
      - name: pass_id
        data_tests: [unique, not_null]
      - name: status
        data_tests:
          - accepted_values:
              values: ['active', 'ended', 'expired']
      - name: school_id
        data_tests:
          - relationships:
              to: ref('stg_app__schools')
              field: school_id
  • Generic tests: the four built-ins above (unique, not_null, accepted_values, relationships), plus many more from the dbt_utils and dbt_expectations packages.
  • Singular tests: any SQL file in tests/ that returns bad rows, e.g. "no pass ends before it starts".
  • Unit tests (dbt 1.8 and later): feed a model fixed input rows and check the exact output. This tests the logic itself, like your golden-file tests in AscendAI.
  • Model contracts: lock a mart's column names and types, so a change that would break a dashboard fails the build instead.

Source freshness: catching a silent Stitch failure

sources:
  - name: app
    database: raw
    loaded_at_field: _sdc_batched_at
    freshness:
      warn_after: {count: 6, period: hour}
      error_after: {count: 24, period: hour}
    tables:
      - name: hall_passes

dbt source freshness checks when each source last received data. If Stitch quietly stops syncing, this fails before anyone notices stale numbers in a dashboard. It's a direct answer to "a stack that runs on good intentions today."

The review workflow

The posting asks you to "set the standard for how data work gets reviewed when a model can write the first draft." In dbt, that standard is the pull request plus CI:

  • Environments: each developer builds into their own schema (dbt_william) using a dev target. Production builds into analytics. Same code, different target in profiles.yml.
  • Slim CI: dbt build --select state:modified+ --defer --state prod-artifacts/ builds only what changed plus downstream, and reads unchanged upstream models from production. Fast and cheap.
  • What a reviewer checks: does the SQL make sense, are keys tested, did row counts change unexpectedly (a "data diff" against production), is new PII tagged, are docs written.
Your angle on AI review

When AI writes the first draft, the risk isn't syntax. It's SQL that runs fine and quietly produces wrong numbers: a join that duplicates rows, a filter that drops a school. The answer is tests that catch exactly that (unique keys, relationships, row-count checks, unit tests on tricky logic), plus a human reading the diff. That's the same discipline as your golden-file tests and your guarded Oracle MCP server: let the model draft, and don't let it ship unchecked.

Snapshots, docs, and grants

Snapshots: keeping history Stitch doesn't

Stitch replicates the current state of a row. If a school's plan changes from Basic to Premium, the old value is gone. A dbt snapshot records each change as a new row with dbt_valid_from and dbt_valid_to (a "slowly changing dimension, type 2"). Finance and RevOps usually need this for questions like "what was this account's plan at renewal?"

Docs and lineage

dbt docs generate builds a browsable site from your YAML descriptions, with the lineage graph above. Exposures let you declare which Metabase dashboards depend on which models, so you can see what breaks before you change something. This is how analysts learn to self-serve: they look up what a column means instead of asking you.

Access control as code

# dbt_project.yml
models:
  minga:
    marts:
      +materialized: table
      +grants:
        select: ['REPORTER', 'ANALYST']

dbt re-applies grants every time it builds, so permissions can't drift away from what's in git. Snowflake masking policies can be attached to tagged columns from dbt too, which ties this guide to the PII section of the Snowflake guide.

Flashcards
What does dbt actually do?

Compiles SELECT-statement models (SQL + Jinja) into DDL, runs them in the warehouse in dependency order, and tests the results. It doesn't move data.

ref() vs source()?

source() points at raw tables loaded by something else (Stitch). ref() points at another dbt model. Both add edges to the dependency graph.

Name the four built-in generic tests.

unique, not_null, accepted_values, relationships.

When would you make a model incremental?

When it's large and append-heavy (events). Each run processes only new or changed rows, saving time and Snowflake credits.

What is a snapshot for?

Keeping history of rows that get overwritten in the source (type 2 slowly changing dimension), using dbt_valid_from and dbt_valid_to.

What does state:modified+ do in CI?

Selects only models changed in this branch plus their downstream, comparing against the production manifest. Used with --defer for fast "slim CI".

What are staging models allowed to do?

Rename, cast, light cleaning. One per source table. No joins or business logic. They're the only models that read source().

How does dbt help self-serve?

Generated docs with column descriptions and lineage, exposures that link dashboards to models, and a reviewed path for analysts to contribute their own models.

Try it yourself

dbt Core is free, and dbt Labs publishes a sample project called jaffle shop (a made-up sandwich shop) built for learning. Pair it with the Snowflake trial:

  • python -m pip install dbt-core dbt-snowflake, then dbt init and point it at your trial account.
  • Load the jaffle shop CSVs with dbt seed, or declare a Snowflake sample table as a source.
  • Write two staging models and one mart that joins them, using ref().
  • Add unique and not_null tests, break one on purpose, and watch dbt build fail.
  • Convert the mart to incremental and run it twice.
  • Run dbt docs generate and dbt docs serve and look at the lineage graph.
  • Put it in a GitHub repo with a GitHub Actions job that runs dbt build on pull requests. That's a small, real demo of "review standards for data work."

Airflow Field Guide

Apache Airflow is the best-known orchestration tool, the thing that runs each pipeline step in the right order and tells you when one fails. The posting says Minga's stack "runs on good intentions today." This guide explains what orchestration would change.

The one-minute version

  • You write workflows in Python as DAGs (directed acyclic graphs): a set of tasks plus the order they run in.
  • Airflow's scheduler starts each run on time, runs each task once the tasks before it succeed, retries failures, and records every run's state.
  • It's a conductor, not an engine. Tasks tell other systems (Stitch, Snowflake, dbt) to do the heavy work, then wait for the result.
  • Version 3.0 came out in April 2025 with a new UI, DAG versioning, and "assets" for data-aware scheduling. Most tutorials online still show version 2.
  • Alternatives in the same category: Dagster and Prefect. The posting only asks for working knowledge of at least one orchestration tool, so any of them counts.
Where it sits at Minga

The posting: "Own ingestion end to end: harden or replace our current Stitch pipelines and bring proper orchestration to a stack that runs on good intentions today."

The problem it solves

Without an orchestrator, each tool runs on its own clock. Stitch syncs on its schedule, dbt runs at a fixed time on a cron job, and everyone hopes the load finished first. Usually it does. When it doesn't, dashboards show half-loaded data and nobody gets told.

An orchestrator gives you four things the stack lacks today: dependencies (run B after A succeeds), retries (try a flaky API call again), alerting (tell someone when it fails), and history (what ran, when, how long, and what broke).

nightly_warehouse()
  • >> sets the order. Passing trigger_stitch_sync() into wait_for_stitch sets it too, and hands over the job ID.
  • mode="reschedule" frees the worker slot between checks instead of holding it for 3 hours.
  • Running dbt as one dbt build task is the simplest option. The open-source Cosmos package (from Astronomer) instead turns each dbt model into its own Airflow task, so you can see and retry a single model.
How Airflow runs
  • Executor: how tasks reach workers. LocalExecutor runs them on the same machine. CeleryExecutor uses a queue (Redis) and a pool of workers, like n8n's queue mode. KubernetesExecutor starts a pod per task.
  • Keep DAG files light. The DAG processor re-parses them constantly, so no database calls or API calls at the top level of the file.
  • Managed Airflow means someone else runs all of this: Astronomer (Astro), Amazon MWAA, or Google Cloud Composer. For a one-person data team, that's usually the right call.

Flashcards
What is a DAG?

A directed acyclic graph: a workflow's tasks and the order they run in, with no loops. In Airflow, a Python file.

Operator vs sensor?

An operator does something (run SQL, run a command). A sensor waits for something (a file, an API status) before the next task starts.

What does the scheduler do?

Decides which DAG runs and tasks are due, based on schedules and whether upstream tasks succeeded, and queues them for workers.

Why must tasks be idempotent?

So retries and backfills are safe: running a task twice for the same interval gives the same result instead of duplicates.

What is catchup?

Whether Airflow automatically runs every missed interval since start_date. Off by default in Airflow 3. Backfills do it on purpose.

Where do credentials live?

In Airflow Connections, optionally backed by a secrets manager. Never in DAG code.

What's the main difference with Dagster?

Airflow schedules tasks. Dagster models data assets (tables, models) and their lineage, which fits dbt naturally.

What changed in Airflow 3?

Released April 2025: new React UI, DAG versioning, assets (renamed from datasets), a Task Execution API between workers and the core, and catchup off by default.

A classic task: flatten a nested document into columns. In Snowflake you'd do this with LATERAL FLATTEN on a VARIANT column, and that's usually the better place. But you should be able to write it in Python too:

flatten.py

def flatten(d: dict, parent: str = "", sep: str = "_") -> dict:
    """{"student": {"id": 42}} -> {"student_id": 42}. Lists are kept as-is."""
    out = {}
    for key, value in d.items():
        name = f"{parent}{sep}{key}" if parent else key
        if isinstance(value, dict):
            out.update(flatten(value, name, sep))
        else:
            out[name] = value
    return out

flatten({"_id": "abc", "student": {"id": 42, "name": "Ana"}, "tags": ["late"]})
# {"_id": "abc", "student_id": 42, "student_name": "Ana", "tags": ["late"]}

Arrays are the hard part. A document with three tags becomes three rows in a child table (like FLATTEN in Snowflake, or a detail table in Oracle). Say that out loud in an interview. It shows you know where the real modelling decision is.

Dates and time zones

Schools are spread across US time zones, and "tardy at 8:05" means local time. Store UTC, convert for display.

time.py

from datetime import datetime, timezone, timedelta

Generators and batching

A generator produces values one at a time with yield instead of building a whole list in memory. It's how you stream a million rows without loading them all at once, much like fetching from a cursor.

batching.py

from itertools import batched     # Python 3.12+

def read_events(path: str):
    with open(path, encoding="utf-8") as f:
        for line in f:                   # one line at a time, not the whole file
            yield json.loads(line)

for chunk in batched(read_events("events.jsonl"), 5000):
    load_to_snowflake(chunk)                # chunk is a tuple of up to 5,000 events

Generator expressions use parentheses: total = sum(e["points"] for e in events) adds them up without building a list first.

Calling APIs

You've done this in the n8n stack (HubSpot, Jira, GitHub, Vercel). In Python the standard library is requests. The three things that matter are pagination, retries and incremental loads.

hubspot_contacts.py

import os, time, logging, requests

log = logging.getLogger(__name__)
BASE = "https://api.hubapi.com/crm/v3/objects/contacts"
session = requests.Session()
session.headers["Authorization"] = f"Bearer {os.environ['HUBSPOT_TOKEN']}"  # secret from env, never in code

def get_with_retry(url: str, params: dict, tries: int = 5) -> dict:
    for attempt in range(tries):
        resp = session.get(url, params=params, timeout=30)
        if resp.status_code == 429 or resp.status_code >= 500:
            wait = 2 ** attempt                     # 1, 2, 4, 8, 16 seconds
            log.warning("HTTP %s, retrying in %ss", resp.status_code, wait)
            time.sleep(wait)
            continue
        resp.raise_for_status()                     # 4xx other than 429: fail loudly
        return resp.json()
    raise RuntimeError(f"gave up after {tries} tries: {url}")

def all_contacts():
    params = {"limit": 100}
    while True:
        page = get_with_retry(BASE, params)
        yield from page["results"]
        after = page.get("paging", {}).get("next", {}).get("after")
        if not after:
            break
        params["after"] = after                     # cursor pagination
  • Retry only what's retryable. 429 (rate limited) and 5xx (server trouble) are worth retrying. A 401 or 404 won't fix itself, so fail. You learned this with GitHub's ambiguous 404s.
  • Always set a timeout. Without one, requests can hang forever.
  • Incremental loads. Don't pull everything every night. Remember the highest updated_at you loaded (the "watermark"), and next run ask only for records changed since then, minus a small overlap for safety. The overlap means some rows arrive twice, which is why the load must be idempotent (a merge, not an insert).

The one rule

Never build SQL with an f-string or +. f"WHERE email = '{email}'" is SQL injection waiting to happen, and it breaks on names like O'Brien. Pass values as parameters. The placeholder style varies by driver: %s for Snowflake and psycopg (PostgreSQL), :name for oracledb, same idea as bind variables in PL/SQL.

For loading big batches into Snowflake, row-by-row inserts are slow. The fast paths are write_pandas (from snowflake.connector.pandas_tools, which stages a file and runs COPY INTO), or writing files to a stage yourself and running COPY INTO. Then MERGE from the staging table into the target so reruns don't duplicate rows.

Pipeline habits that matter more than syntax
  • Idempotent. Running a job twice gives the same result as running it once. Load into staging, then MERGE on a key. Or replace a whole date partition. Never blind INSERT on a rerun. Your CDWTool duplicate protection per reporting period is the same idea.
  • Small, pure functions. Separate "fetch" (talks to the network), "transform" (pure: data in, data out) and "load" (talks to the warehouse). The transform is where bugs live, and a pure function is trivial to test.
  • Tests with pytest. Plain functions starting with test_ and plain assert.
  • Logging, not print. Log counts in and counts out. "Loaded 0 rows" should be visible, and maybe alarming.
  • Config and secrets from the environment (or a secrets manager). Nothing sensitive in git. Same rule you applied when you removed committed secrets from CDWTool.
  • Fail loudly. A pipeline that swallows an exception and reports success is worse than one that crashes. Then test the alert path on purpose, like your n8n canary.

Gotchas interviewers like
Mutable default arguments

def add(x, items=[]): reuses the same list on every call, so it keeps growing. Use items=None and create the list inside the function.

is vs ==

== compares values. is checks that two names point at the same object. Use is only for None.

Copies

b = a doesn't copy a list or dict, it gives the same object a second name. a.copy() makes a shallow copy. Nested dicts need copy.deepcopy.

Floats and money

0.1 + 0.2 != 0.3. For revenue, use decimal.Decimal in Python and NUMBER(p,s) in Snowflake. Ted will care.

"How would you load data from an API Stitch doesn't cover?"
"Incremental pulls using an updated-since watermark with a small overlap, cursor pagination, retries with backoff only on rate limits and server errors, and a timeout on every call. Land it raw in a staging table, then merge on the key so a rerun can't duplicate anything. Log the counts in and out, and make sure a failure actually alerts someone. I'd test that by forcing a failure, the same way I tested my n8n error handler."
"How do you review AI-written Python?"
"Same as any code. I read every line, I check that queries are parameterized and secrets come from the environment, and the transform logic gets unit tests with real edge cases: empty input, nulls, duplicates, time zones. The model drafts, I approve. If I can't explain a line, it doesn't ship."
Keep it accurate

Don't claim pandas, Airflow or Snowpark in production. Do claim what's true: Python scripting for pipelines and tooling, the n8n workflow generator, REST API integration, and deep SQL. If you build the small project below this week, you can describe exactly what you built.

Flashcards
List comprehension that keeps active student ids?

[s["id"] for s in students if s["active"]]

Get a dict value without risking KeyError?

d.get("key") or d.get("key", default).

What does yield do?

Turns the function into a generator: it hands back one value at a time and pauses, so you can stream large data without holding it all in memory.

How do you pass a value into SQL safely?

As a bound parameter: cur.execute("... WHERE id = %s", (id,)). Never format it into the string.

Which HTTP errors are worth retrying?

429 (rate limited) and 5xx (server errors), with exponential backoff. Not 400, 401, 403 or 404.

What makes a load idempotent?

A rerun can't change the result: load to staging and MERGE on a key, or replace the whole partition. No blind inserts.

Naive vs aware datetime?

Naive has no time zone. Aware does. Use datetime.now(timezone.utc) and keep everything aware.

Why is def f(items=[]) a bug?

The default list is created once and shared by every call, so it accumulates values.

Fastest way to find ids in one list but not another?

Sets: set(a) - set(b).

When pandas, when SQL?

pandas for exploration and one-off files. Recurring transformation goes in SQL/dbt in the warehouse, where it's tested, reviewed and runs on warehouse compute.

Try it yourself (about two hours)

A small project that ties this guide to the Snowflake and dbt guides, so you can talk about it from your own hands-on time:

  • Your machine has Python 3.11. itertools.batched needs 3.12 or newer, so install 3.12+ (or use uv, which can fetch it), or slice batches yourself with islice on 3.11.
  • Make a folder, run python -m venv .venv, activate it, and pip install requests snowflake-connector-python pytest.
  • Write a fake source: a JSON-lines file of 1,000 "hall pass" events with nested student and school objects and a created_at in UTC. Have Claude generate it, then read it.
  • Write transform.py with flatten() and a validator that splits good and rejected rows. Write pytest tests for both, including empty input and a missing field.
  • Write load.py that batches the good rows into a RAW.EVENTS_STAGE table in your Snowflake trial with parameterized inserts, then runs a MERGE into RAW.EVENTS on the event id.
  • Run it twice and confirm the row count doesn't change. That's your idempotency proof.
  • Point a dbt staging model at RAW.EVENTS and you've built a small end-to-end pipeline: Python loads, dbt transforms, tests guard both.
